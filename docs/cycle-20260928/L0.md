# L0 - Local REST API 5.3.1 compatibility

## What the candidate proves

The embedded specification is pinned to the upstream 5.3.1 commit and blob in
../obsidian-api/source.json. YAML is unchanged, including upstream trailing
blanks; only that vendor file has a scoped whitespace rule. JSON is a structural
projection. Neither the snapshot nor a version number proves live readiness.

New tests exercise the production Axios adapter using actual local HTTP sockets
and an in-memory disposable fixture: Bearer authentication, rich-path encoding,
root/active reads, HEAD metadata, typed JSON PATCH, unchanged heading payloads,
pre-dispatch rejection, nine error classes, redaction, single dispatch and timeout.

The heading test proves client payload preservation, NOT the server's rebasing
semantics. Use a governed body/full-note writer when exact Markdown is required.
An HTTP 200 is not proof of literal heading output.

## Version policy

- 5.1.0 is the historical core baseline, not a security recommendation. Upstream
  path-containment fixes must not be dismissed because the older adapter works.
- 5.3.1 is this pinned qualification target, not yet an installed-runtime
  certification. Existing availability and authorization gates remain.
- Do not invent a hard minimum or certification for earlier/later versions.
  New optional capabilities need concrete negotiation.

getAPI is a typed helper over getPublicApi, not a second mutation authority.
Existing addRoute registrations must not require API v3 merely for documentation.
OpenAPI declarations describe routes; they never authorize them.

## Disposable Desktop gate - NOT_RUN

Do not upgrade/reload production plugins or regenerate certificates to run this
gate. First obtain authorization and attest a disposable vault and its endpoint.
No real vault content or credentials belong in public CI or evidence.

1. Record candidate SHA and built artifact hashes. Install pinned Local REST
   5.3.1 and the candidate Bridges only in the authorized pilot; preserve grants.
2. Verify authenticated root and all Bridge status routes. Separate observed
   versions, optional capabilities and authorization.
3. Exercise one synthetic Markdown fixture: typed frontmatter PATCH, rich paths,
   real heading rebasing and stale ifMatch rejection. Verify actual postconditions
   and restore through the owning API.
4. Read scripts/smoke-bridge-lifecycle-live.mjs before running its existing gated
   canary. It checks a fixed pilot vault, URL and confirmation. Override expected
   Bridge versions from candidate manifests, not historical example defaults.
   Prove late startup, unregister/reload/remount and unchanged grants with a
   surviving MCP client. Negative write permissions remain part of the gate.
5. Characterize SSE separately: normal auth, signed URLs off, expiry and reload.
   No file.content does not mean no metadata. Counter gaps do not prove loss.
   This alone does not prove L1 cache behavior.
6. Characterize raw binary HTTP separately from MCP previews. Signed PUT can
   overwrite; it is not a governed create. A reduced preview is not an original.
   This alone does not prove L2 import or remote-client byte transport.
7. Record restoration and pending recoveries. Incomplete restoration blocks
   qualification. Use status/recovery, not another mutation after a lost reply.

A missing pilot is NOT_RUN. Repository fixture passes never replace TLS trust,
installed lifecycle, native writer or real remote transport verification. See
this lot's PR for current CI, review, tested SHA and first incomplete gate.

## Review repairs

The first distinct review (36978e8) requested explicit loopback proxy isolation,
complete CI dependency filters, and cryptographic commit-to-path provenance.
The fixture restores its environment and is tested under a hostile loopback
proxy. Both workflow triggers cover src, package files and checkout attributes.

object hash is verified before traversing tag -> commit -> docs/openapi.yaml ->
vendor blob. This verifies association, not the upstream author's identity.
