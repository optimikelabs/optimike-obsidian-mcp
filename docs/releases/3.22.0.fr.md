# Version 3.22.0 — Des formules de Base vérifiées par le moteur d'Obsidian lui-même

La 3.22.0 permet aux agents de vérifier les formules de Base et le Markdown d'après ce que fait réellement Obsidian, et non d'après une copie de ses règles.

- **Le moteur Bases d'Obsidian par le Bases Bridge (PR #178) :** `POST /extensions/obsidian-bases-bridge/engine/evaluate` calcule chaque formule d'une Base, telle qu'enregistrée ou à partir d'un YAML candidat en mémoire, avec le moteur d'Obsidian, et rend pour chaque formule `ok`, `syntax_error`, `runtime_error`, `all_null` ou `not_evaluated`. Une formule témoin correcte et une fautive sont vérifiées à chaque appel ; si elles ne se comportent pas comme prévu, la réponse est `available: false`. `GET .../engine/functions` rend les fonctions de formule de l'Obsidian installé, lues dans l'application en cours.
- **`bases_query` calculé par le moteur (PR #179) :** avec `evaluate` (par défaut), les lignes, les filtres de la vue, le tri, la limite et les valeurs des formules viennent d'Obsidian (`source: "engine"`), y compris les formules que l'ancien évaluateur du Bridge ne savait pas calculer, comme `link(file, file.name)`. Sans le moteur, `source: "fallback"` ne rend aucune valeur de formule plutôt qu'une valeur devinée. L'évaluateur privé du Bridge est retiré.
- **Plans de Base refusés avant scellement (PR #181) :** `bases_formula_patch_plan` et `bases_config_patch_plan` évaluent la Base telle qu'elle est et telle que prévue. Un plan qui fait passer une formule en erreur de syntaxe ou de calcul est refusé avec `base_formula_engine_error` : rien n'est scellé ni écrit, et `formulaCheck` donne les messages du moteur, les fonctions inconnues, les fonctions valides pour le type et les noms proches (`lowr` propose `lower`). Les erreurs déjà présentes ne bloquent pas ; une formule toujours vide est un avertissement. Le reçu porte `engineCheck` : `verified` avec la version d'Obsidian, ou `unverified` avec une raison.
- **`bases_functions` et `bases_check` (PR #182, ticket #176) :** en lecture seule. `bases_functions` liste les fonctions de formule de l'Obsidian installé par type, ou les signatures d'un type. `bases_check` donne l'état des formules d'une Base ou de toutes les Bases ; un moteur indisponible, un Obsidian fermé ou un Bases Bridge absent donnent `unverified`, jamais un état sain.
- **`obsidian_validate_format` vérifie le Markdown contre le coffre ouvert (PR #180, ticket #177) :** avec Atomic Write Bridge 0.10.0 : liens et intégrations qui ne mènent à aucun fichier, titres et identifiants de bloc absents, types de callout inconnus d'Obsidian, du thème et des extraits CSS, et valeurs de propriétés contre leur type déclaré. Seuls les problèmes que le contenu ajoute au fichier actuel sont signalés. Le code est ignoré, y compris un bloc de code dans une citation ou un callout et le code en retrait. Sans le Bridge, les contrôles statiques restent et `vaultCheck` indique que le coffre n'a pas été vérifié.

Vérifié en conditions réelles sur un coffre jetable avec Obsidian 1.15.1 : le moteur répond en 3 à 150 ms par appel (les 150 ms correspondent à `bases_check` sur 10 Bases) ; les plans refusés ont laissé la Base inchangée octet pour octet ; une note de test comportant sept problèmes les a tous rendus, et une note existante relue telle quelle n'en a rendu aucun.

**Bridges :** Bases Bridge 1.3.0 et Atomic Write Bridge 0.10.0 sont livrés dans le bundle de cette release ; Operon Bridge 0.9.9 est inchangé. Installez ensemble le MCP et le bundle des Bridges de la même release, Obsidian fermé (voir [Bridge packaging](../bridge-packaging.md)). Avec des Bridges plus anciens, les nouveaux contrôles répondent `unverified` ou sautent la vérification du coffre ; rien ne casse. Voir le [changelog](../../CHANGELOG.md#3220---2026-11-20).
