# Version 3.23.0 — Les agents trouvent le bon outil Obsidian et peuvent demander avant d'écrire

La 3.23.0 aide les agents qui chargent leurs outils par recherche à trouver ceux de ce serveur avant ceux d'un autre serveur, et permet à un client de poser une question native oui/non avant l'écriture d'un patch de texte gouverné.

- **Indices de recherche sur 32 points d'entrée (PR #191, ticket #190) :** les lectures de notes, de Bases et de canvas, les outils gouvernés `*_plan` et les outils de tâches Operon portent un court `_meta["anthropic/searchHint"]` avec les mots d'usage absents de leur nom (par exemple `operon_transition_task` : « mark done, complete, cancel, reopen, change status »). Les indices vont sur les plans, jamais sur les étapes apply, status ou recover. Les noms, descriptions, schémas d'entrée, annotations, profils et capacités annoncées ne changent pas ; les clients qui ne connaissent pas la clé l'ignorent. Sur 78 requêtes par mots-clés tenues à l'écart et classées comme le fait Claude Code 2.1.331, l'outil attendu est dans les 3 premiers pour 57 au lieu de 46, et premier pour 47 au lieu de 27. Dans de vrais runs Claude Code, l'outil final était le bon dans 144 runs sur 156, contre 127 sur 152 avant. Codex filtre les outils dans son propre code et ne lit jamais `_meta` : inchangé.
- **Des instructions serveur qui demandent le mot `obsidian` (PR #194, ticket #192) :** les instructions MCP commencent maintenant toujours par une phrase qui demande au client de mettre `obsidian` dans ses recherches d'outils, car d'autres serveurs connectés peuvent avoir des outils aux mêmes verbes (`add_note`, `update_task`). Le paragraphe sur les fichiers d'instructions du coffre suit inchangé ; un client qui ne recevait aucune instruction reçoit maintenant cette seule phrase. À côté des catalogues rejoués de Rize, Brevo, Claude Docs et T3, sur 64 runs Claude Code : bon outil final 61 → 63, outil d'écriture d'un autre serveur choisi 3 → 1, recherches contenant `obsidian` 7/43 → 57/63, aucun cas juste avant et faux après. Le mot agit par le nom configuré du serveur et par les noms d'outils `obsidian_*` : garder `obsidian` dans la clé du serveur, comme dans `optimike-obsidian-mcp-stdio`. Voir [Profils de surface d'outils](../tool-surface-profiles.fr.md).
- **Confirmation facultative de l'apply (PR #189, ticket #188) :** désactivée par défaut. Avec `MCP_PROTOCOL_MODE=dual` et `MCP_APPLY_CONFIRMATION=elicit`, `obsidian_text_patch_apply` pose au client une question oui/non avant d'écrire, si le client déclare l'élicitation par formulaire. La question nomme la cible, les types d'opérations, les clés de frontmatter modifiées et le `planRef`, jamais le texte scellé. Accepter applique le plan scellé exact sous le CAS habituel et le reçu ajoute `confirmation: "elicited"` ; refuser rend `apply_confirmation_declined`, rien n'est écrit et le plan reste `planned` : l'appliquer de nouveau repose la question. L'annulation, une réponse invalide ou expirée, une erreur du client ou du relais et une note modifiée depuis le plan sont aussi des refus fermés. Une acceptation peut venir d'un hook de l'hôte : elle ne prétend jamais qu'une personne a cliqué. Derrière le proxy stdio, le proxy et le backend ont tous deux besoin du réglage. Voir [Confirmation facultative de l'apply](../governed-text-patch-p4.fr.md#confirmation-facultative-de-lapply-élicitation).
- **Évaluation de la découverte des outils (PR #191) :** `evals/tool-discovery-corpus.json` et `scripts/run-tool-discovery-eval.mjs` reproduisent le classement de Claude Code sans modèle, lancent de vrais runs Claude Code et des sessions Codex isolées contre un serveur de rejeu qui ne sert que le catalogue et refuse tout appel d'outil, et peuvent servir à côté les catalogues d'autres serveurs. Voir les [évaluations de routage](../../evals/README.md).
- **Dépôt :** l'en-tête de la LICENSE cite d'abord le titulaire actuel des droits (PR #186), et la CI saute les suites runtime pour un changement limité à LICENSE ou NOTICE tout en rapportant les checks requis (PR #187).

Les mesures ont été faites sur un coffre synthétique vide, avec des catalogues rejoués et aucun outil exécuté ; les échantillons sont petits (2 runs par cas pour Claude Code), le changement dans la formulation des recherches est donc le signal solide. Non vérifié : la carte d'élicitation d'un vrai hôte, et les clients qui ignorent les instructions serveur MCP (ils ne voient aucun changement).

**Bridges :** aucun changement de Bridge. Atomic Write Bridge 0.10.0, Operon Bridge 0.9.9 et Bases Bridge 1.3.0 sont livrés inchangés dans le bundle de cette release : passer de la 3.22.0 à la 3.23.0 ne demande pas de réinstaller les Bridges. Voir le [changelog](../../CHANGELOG.md#3230---2026-11-25).
