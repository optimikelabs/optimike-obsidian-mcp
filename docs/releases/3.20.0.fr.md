# Version 3.20.0 — Épingles, modifications par lot et schémas d'outils qui disent vrai

La 3.20.0 permet aux agents d'épingler et de désépingler une tâche Operon, et de modifier plusieurs tâches dans un seul plan scellé. Elle corrige aussi les schémas d'outils et les refus qui avaient fait croire à un agent qu'une tâche ne pouvait pas être créée dans une note (issues #159 et #160).

- **Épingler et désépingler (`operon_set_pinned`) :** pose l'état épinglé d'une tâche précise par l'API Developer d'Operon (`tasks.pinned`, risque `routine`, contrôle de l'état avant écriture). L'épinglage se négocie dans une session à part, au premier usage : tant que le propriétaire du coffre n'a pas approuvé `tasks.pinned.preview` et `tasks.pinned.apply` dans les réglages d'Operon (Core → General → Developer API Integrations), l'outil refuse avec `capability_pending_approval` et tous les autres outils Operon continuent de fonctionner. Après l'écriture, le Bridge relit l'état épinglé ; un état non confirmé est signalé comme incertain.
- **Modification par lot (`operon_update_tasks`) :** modifie les champs gérés de 2 à 64 tâches précises dans un seul plan, avec l'autorisation `tasks.update` existante (aucune nouvelle approbation). Chaque `expectedRevision` est vérifiée avant le plan, puis juste avant l'écriture ; une seule révision périmée refuse tout le plan, sans rien écrire. Chaque tâche est relue après l'écriture.
- **Des schémas d'outils sans références partagées :** les schémas d'entrée ne fusionnent plus deux champs en `$ref`. `operon_create_task` publiait `task.targetPath` comme une copie de `targetFolder`, avec sa description « ancien routage, refusé » ; `targetPath` a maintenant sa propre description : la note qui reçoit une tâche inline. Les valeurs récursives restent précises grâce à des définitions locales. Un test échoue si un schéma d'outil renvoie à une autre propriété.
- **Des refus qui nomment le champ :** un argument invalide d'un outil Operon renvoie maintenant `VALIDATION_ERROR`, avec `reasonCode: invalid_tool_arguments` et `validationIssues` (chemin du champ et raison), au lieu de `INTERNAL_ERROR`. Les messages viennent d'une liste fermée écrite par les auteurs ; les clés des objets libres (`fields.*`, `properties.*`) sont masquées, et les valeurs reçues ne sont jamais renvoyées.
- **Une description plus claire pour `operon_create_task` :** `targetPath` sert aux tâches inline ; une tâche fichier va toujours dans le dossier configuré d'Operon ; `fields.related` attend des identifiants de tâches Operon, les liens vers une note vont dans `fields.links`.

Installer le MCP 3.20.0 avec le bundle des Bridges de la même release (Operon Bridge 0.9.9, Atomic Write Bridge 0.9.2, Bases Bridge 1.2.2). Approuver ensuite une fois l'épinglage dans les réglages d'Operon pour utiliser `operon_set_pinned` ; rien d'autre ne change pour les clients. Suites : #154, #155, #156, #164. Voir le [changelog](../../CHANGELOG.md#3200---2026-11-12).
