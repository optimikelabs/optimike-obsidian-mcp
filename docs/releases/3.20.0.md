# Version 3.20.0 — Pins, batch updates and tool schemas that tell the truth

3.20.0 lets agents pin and unpin Operon tasks and update several tasks in one sealed plan, and fixes the tool schemas and refusals that led an agent to believe a task could not be created inside a note (issues #159 and #160).

- **Pin and unpin (`operon_set_pinned`):** sets the pinned state of one exact task through Operon's Developer API (`tasks.pinned`, risk `routine`, compare-and-set). Pins are negotiated in their own session on first use: until the vault owner approves `tasks.pinned.preview` and `tasks.pinned.apply` in Operon settings (Core → General → Developer API Integrations), the tool refuses with `capability_pending_approval` and every other Operon tool keeps working. After apply, the Bridge reads the pinned state back; an unconfirmed state is reported as uncertain.
- **Batch update (`operon_update_tasks`):** updates managed fields of 2 to 64 exact tasks in one plan, under the existing `tasks.update` grant (no new approval). Every `expectedRevision` is checked before the plan and again just before apply; one stale revision refuses the whole plan without a write. Each task is read back after apply.
- **Tool schemas without shared references:** tool input schemas no longer collapse repeated fields into `$ref`. `operon_create_task` used to publish `task.targetPath` as a copy of `targetFolder`, with its "legacy, rejected" description; `targetPath` now has its own description: the destination note of an inline task. Recursive values stay precise through local definitions. A test fails if any tool input schema references another property.
- **Refusals that name the field:** an invalid Operon tool argument now returns `VALIDATION_ERROR` with `reasonCode: invalid_tool_arguments` and `validationIssues` (field path and reason) instead of `INTERNAL_ERROR`. Messages come from a closed list written by the authors; keys of free-form objects (`fields.*`, `properties.*`) are masked, and received values are never echoed.
- **Clearer `operon_create_task` description:** `targetPath` is for inline tasks; a file task always goes to Operon's configured file-task folder; `fields.related` takes Operon task ids, note links go in `fields.links`.

Install MCP 3.20.0 with the Bridge bundle of the same release (Operon Bridge 0.9.9, Atomic Write Bridge 0.9.2, Bases Bridge 1.2.2). Then approve the pin capability once in Operon settings to use `operon_set_pinned`; nothing else changes for clients.
