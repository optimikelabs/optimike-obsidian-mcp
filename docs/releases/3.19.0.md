# Version 3.19.0 — FDM-dated notes unblocked and vault agent instructions

3.19 fixes governed edits of notes that Frontmatter Date Manager dates from their real file creation time, and makes the vault's `AGENTS.md` files reach agents that see the vault only through MCP.

- **Notes dated by FDM no longer stay locked (issue #147):** when a plan targets a note without `création`, FDM 1.6.0 fills it from the file creation time, which is earlier than the plan. 3.18 rejected that date and left the note locked with `date_preparation_unverified`, for example a note created by the MCP and patched more than a minute later. Atomic Write Bridge 0.9.2 now returns the file stat it observed just before the FDM command (`datePreparation.fileStat`) and refuses the preparation if the creation time moves. The MCP checks each date by its role, for the text patch, frontmatter patch, note replacement and Base rows: an added creation must equal the observed file creation time exactly, in FDM's format; a modification must equal the observed modification time or fall inside the request window. Every other guard is unchanged (fresh read, non-date bytes, existing creation, fence, lock, no replay). FDM still writes every date; the MCP never writes one.
- **Install Atomic Write Bridge 0.9.2 with the MCP:** with an older Bridge, a plan on a note that needs a date preparation is refused before any lock or change with `date_preparation_bridge_upgrade_required` (`mutationMayHaveApplied: false`): update the Bridge, then plan again. Notes already dated, or outside date management, keep working with an older Bridge.
- **Clearer refusal:** `date_preparation_unverified` now carries `preparationCheck`, a closed sub-cause without path or value (for example `created_provenance_mismatch`), also logged as a warning.
- **Notes already locked:** updating the MCP and the Bridge does not release a lock left by 3.18 or earlier. Follow [notes locked by a date preparation](../administrative-closure.md#notes-locked-by-a-date-preparation): check the note, then `obsidian_operation_close` with `datePreparationPaths`, first in dry run.
- **Vault agent instructions (`AGENTS.md` cascade):** for every governed plan and direct write, the server finds the instruction files that apply to the paths it really writes (the vault root, then each parent folder of each target) and reports them in `vaultInstructions`, with whether this reader has read each one in its current version. The server instructions tell the agent to read them. A read is proven by the SHA-256 of the content `obsidian_read_note` served. Targets include both Unicode spellings of a path, Operon file-task destinations and the notes whose links a native move rewrites.
- **Modes:** `MCP_VAULT_INSTRUCTIONS` = `off` (as before), `advise` (default: reports, never refuses) or `enforce` (refuses before the tool runs while an applicable file is unread or changed, and refuses apply or recover when the rules changed after the plan). `MCP_VAULT_INSTRUCTIONS_MIN` sets an administrative minimum, `MCP_VAULT_INSTRUCTIONS_FILES` the file names, Markdown only (default `AGENTS.md`), `MCP_VAULT_INSTRUCTIONS_JOURNAL_PATH` the plan seal journal. Each client chooses its mode through its stdio proxy. See [vault agent instructions](../vault-instructions.md).
- **Vault without instruction files:** `off` changes nothing. `advise` keeps results unchanged but adds the folder probes. `enforce` still refuses writes whose target cannot be determined (active file, periodic Operon task creation, inline Operon task without `targetPath`, vault-wide tag rename), any plan or apply while the seal journal cannot be opened, and the apply of a plan made with the mode off.
- **Known limits:** the server proves that the agent received the instructions before writing, not that it follows them. Only writes through this server are checked; notes Operon writes on its own after a mutation and `operon_recover_mutation` are not. A read under a mixed NFC/NFD spelling is not attached to the merged entry: read the displayed path again.

Install MCP 3.19.0 with the Bridge bundle of the same release (Atomic Write Bridge 0.9.2, Operon Bridge 0.9.7, Bases Bridge 1.2.2), after draining pending operations and date preparation fences. No Bridge setting or grant changes. To keep the previous behaviour exactly, set `MCP_VAULT_INSTRUCTIONS=off`. Not tested: macOS, and live Operon creation with a parent only. See the [changelog](../../CHANGELOG.md#3190---2026-11-05).
